The rules

Same pixels

Every parity screenshot equals Rails', in every seed. Server HTML, the DOM and Cable frames may differ.

Always correct

No stale read after a write, no data in the wrong user's response. Every cache states its invalidation rule and has tests that try to break it.

Durability is opt-in

Anything that weakens it is measured both ways, documented, and ships behind a setting that defaults to Rails' durability.

Scored twice

Every ratio is against Rust and against the F# port, from the same harness, seed and pinned CPUs, and never called a port result.

The climb

How to read the chart

×

The line is the geometric mean of onCrack's throughput over Rust's across the five benchmarked workloads (room page, messages page, sidebar, search, post a message) at 16 connections. Dots are spaced evenly in the order they ran, not by the clock. A dot that measured only some workloads carries the rest from the last kept run; its card greys them. The dotted line is the F# port's own ratio, where onCrack starts.

Read with care

  • The first dot is not onCrack. It is the F# port's final result (bench/results/phase7-final, 3 reps), the starting point the fork is scored from.
  • Most dots are provisional. Tier 2 runs are one rep of only the workloads a change touches, on a published build mounted into a container. The number that counts is tier 3: a rebuilt image, three reps, all five workloads at 1 and 16 connections.
  • Rust, the port and Rails are stored. Their medians come from one session, bench/results/phase7-final/; onCrack is measured alone against them with the same warm-up, seed and pinned CPUs, not re-measured beside them each time.
  • Rails is in the cards only. At 1 to 2%% of Rust's throughput it would sit flat on the floor of the chart.

Scoring

How onCrack is scored

×

Same harness as the port's Phase 7: bench/run and bench/quick inside colima, the server pinned to CPUs 0-3 and the load generator to 4-7, host networking, the seed parity/.seed/default copied fresh for every run, every route warmed until flat, every response checked, every post's row counted.

Three tiers

  • Tier 1, in process: bench/db-micro and the other micro projects, A/B on one change.
  • Tier 2, mounted: bin/publish-mounted builds the app, bench/quick --mounted runs it over campfire-oncrack:app; one rep of the workloads the change touches.
  • Tier 3, the rebuilt image: all five workloads at 1 and 16 connections, 3 reps. This is a dot's number.

The references

Stored medians of bench/results/phase7-final/: Rust, the F# port (campfire-fsharp:app, left untouched) and Rails, measured in one session. bench/quick compare DIR prints an onCrack run against Rust and against the port; every run is logged with bench/quick log and appears here. A session can also measure all four at once: bench/run --apps reference,rust,fsharp,oncrack.

Pixels

bin/pixel-parity runs the parity harness against Rails and reports only the screenshot layer, per seed. It is the one-command check of “the UI is identical”.

The rules

What onCrack may and may not do

×

From plans/oncrack.md: “Make the UI exactly the same, but go unhinged with Datastar, caching, or any other improvements we can do.” The port matched the Rust port's work per request and beat it 1.18-1.41×. onCrack drops that constraint, and nothing else.

  1. The UI is identical. Every parity screen's pixels match Rails' (the harness's screenshot layer, lean matrix, all seeds) and every interaction behaves the same for a person using it. Server HTML, the live DOM, network requests and Cable frames may differ.
  2. Correct, always. No stale reads after a write, no data from one user in another's response, no lost messages. Every cache states its invalidation rule and has tests that try to break it (concurrent writers, two users with different memberships, bans, deletes, edits).
  3. Durability is a disclosed choice. Group commit windows and synchronous=NORMAL are measured both ways, documented, and shipped only behind a setting whose default is Rails-equivalent durability.
  4. Scored separately. Same harness, same seed and pinned CPUs; every ratio against the Rust port and against the F# port, never presented as a like-for-like port result. The image is campfire-oncrack:app.
  5. Same discipline. Measure before and after, one change at a time, log every run to the climb chart, never manufacture a win.

Claimed F#/Rust ratios from the challenge app. They are off the chart on purpose: the pages weren't identical to Rust's, so they don't measure the same work.
